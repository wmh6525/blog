## 1. 문제

입찰공고 1건(공고문 + 첨부문서 + 나라장터 메타)을 받아 **24개 검토 항목의 위반 여부(0/1)** 와 근거 문구를 출력한다. 평가 지표는 24개 항목 각각의 **위반(=1) 클래스 F1을 단순 평균**한 Macro F1이다.

$$\text{Macro F1} = \frac{1}{24}\sum_{i=1}^{24} F1_i, \qquad F1_i = \frac{2 \cdot TP_i}{\hat{P}_i + P_i}$$

여기서 $\hat{P}_i$는 항목 $i$의 예측 양성 수, $P_i$는 실제 양성 수다.

### 1.1 제약 조건

| 항목 | 값 |
|---|---|
| 모델 | `google/gemma-4-26B-A4B-it` **고정**. 파인튜닝·어댑터·가중치 제출 금지 |
| 추론 | **2시간 초과 시 점수 0이 아니라 제출 오류** |
| 서버 | NVIDIA L40S ×1 (VRAM 44.7 GiB) · 7 vCPU · vLLM |
| 평가셋 | **무라벨** 1,853건 |
| 제출 | 하루 1회 |
| 라벨 | 제공 안 됨. dev 200건만 정답 보유 — **자가 라벨링이 과제의 일부** |
| 외부 자료 | 법령은 **배포 패키지 스냅샷으로 고정**. 외부 수집 일체 금지. 추론 코드의 외부 API 호출 금지 |

모델이 고정이고 파인튜닝이 막혀 있으므로, 성능을 움직일 수 있는 레버는 **프롬프트·검색·결정 로직·시간 배분** 네 가지뿐이다.

### 1.2 이 문제를 어렵게 만드는 네 가지

#### (a) 양성이 희소하다

dev 양성률 **3.19%** (4,800셀 중 153개). 항목당 양성이 5~8건뿐이다.

F1의 정의상 한 항목을 전부 0으로 예측하면 그 항목 F1이 **구조적으로 0**이 되어 24개 평균을 그대로 깎는다. 반대로 과잉 예측도 답이 아니다.

```
[ 침묵의 비용 ]
   항목 하나를 전부 0으로 예측 → F1 = 0
                              → Macro F1에서 1/24 = 0.0417 손실
   침묵 항목이 18개면          → 상한이 0.25로 잘린다

[ 과잉의 비용 ]
   실제 양성 6건을 전부 맞히되 60건을 예측
   → F1 = 2·6 / (60 + 6) = 0.18
```

즉 **모든 항목이 무언가를 말해야 하되, 아무거나 말하면 안 된다.** 초기 규칙 전용 버전에서 침묵 항목이 18개였다는 사실이 첫 병목을 그대로 설명한다.

#### (b) 24개 항목이 독립적이지 않다

약 6개 패밀리가 **하나의 트리거 문구를 공유**하고, 구조화 속성으로 갈린다. v13/v14/v15/v17의 gold 근거는 사실상 같은 문장이고, **금액 구간과 경쟁제품 여부**가 항목을 가른다.

게다가 트리거 문구는 거의 모든 공고에 존재한다.

| 패밀리 | 트리거 보유 | 양성 | 트리거 중 양성 |
|---|---:|---:|---:|
| 중소기업 (v13, v14, v15, v17) | 179/200 | 26 | 14.5% |
| 공동수급 (v21) | 118/200 | 6 | **4.2%** |
| 실적제한 (v2, v3, v4, v8) | 108/200 | 16 | 14.8% |

**함의**: "트리거 문구가 있으면 양성"이라는 순진한 규칙은 공동수급에서 정밀도 4.2%를 낸다. 트리거는 **후보 필터**일 뿐이고, 실제 판정은 금액·지분율·지역 같은 **구조화된 값의 비교**로 이루어져야 한다. 이 관찰이 §2의 아키텍처를 직접 낳았다.

#### (c) dev가 test를 정확히 대표하지 않는다

운영진도 토크보드에서 *"dev 라벨은 실제 검토 업무 이력에 기반한 참조용이라 일부 표본에 실무 데이터 특유의 노이즈가 있을 수 있다"* 고 밝혔다. 실측 전이율은 구간에 따라 **24%~75%** 로 흔들린다.

#### (d) 검증 대역폭이 극히 좁다

```
제출 횟수      : 하루 1회
test 표준오차   : 약 0.0106
2σ 검출 한계    : dev 기준 +0.089 규모의 변경이어야 통계적으로 보인다
실제 최대 변경  : +0.032

→ 개별 변경은 리더보드로 검증할 수 없다.
```

이것이 이 대회의 진짜 제약이다. **"제출해서 확인한다"는 전략이 원천적으로 성립하지 않는다.** 따라서 무엇을 채택할지 결정하는 기준을 리더보드 밖에서 세워야 한다 — §5의 주제다.

## 2. 핵심 설계 (1) — 판정을 모델에게 맡기지 않는다

### 2.1 추출 후 결정 (Extract-then-Decide)

```
┌─────────────────────────────────────────────────────────────┐
│ [1단계] 사실 추출 — LLM                                       │
│                                                             │
│   공고문 ──▶ 34개 구조화 필드                                  │
│              실적 요구금액 / 지역 목록 / 최소 지분율            │
│              설명회 일자 / 발주기관 한정 여부 …                 │
│                                                             │
│   ★ 판정하지 않는다. 원문에 적힌 것만 옮긴다.                    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ [2단계] 결정 — Python                                        │
│                                                             │
│   사실 × 나라장터 메타 ──▶ 24개 라벨                           │
│                                                             │
│   금액 비교 · 지역 개수 · 날짜 산술 · 메타 대조                  │
│   = 전부 결정적(deterministic) 연산                           │
└─────────────────────────────────────────────────────────────┘
```

24개 항목을 4B-active 모델에게 매번 암산시키는 대신, **모델은 사실만 추출**하고 **판정은 코드**가 한다.

### 2.2 왜 이 분리가 결정적이었나

| 효과 | 설명 |
|---|---|
| **단위 테스트 가능** | 규칙마다 테스트를 붙일 수 있다. 모델 판정은 테스트할 수 없다 |
| **오류 귀속 가능** | 틀렸을 때 "추출이 틀렸나 규칙이 틀렸나"를 분리할 수 있다 (§8의 77:23 진단이 여기서 나온다) |
| **재채점 무료** | 추출 결과를 캐시하면 규칙만 고쳐 다시 채점하는 것이 공짜다 (§7의 도구) |
| **하한 확보** | GPU가 전혀 동작하지 않아도 규칙 경로만으로 0.5464가 나온다 |
| **일관성** | 금액 비교를 모델이 하면 같은 입력에 다른 답이 나올 수 있다. 코드는 그렇지 않다 |

**측정된 효과**: dev Macro F1 **0.1274 → 0.3111**, 그리고 **침묵 항목 18개 → 1개**.

두 번째 숫자가 더 중요하다. §1.2(a)에서 본 대로 침묵 항목은 Macro F1의 상한을 직접 자른다. 침묵을 18개에서 1개로 줄인 것은 점수를 올린 것이 아니라 **점수가 올라갈 수 있는 공간을 연 것**이다.

## 3. 핵심 설계 (2) — 법정 상수는 반드시 조문에서 확정한다

절반 이상의 항목이 **금액 구간·비율**에 걸린다. 그리고 §1.2(b)에서 본 대로 항목들은 같은 트리거를 공유하고 상수로 갈린다. 따라서 **추측한 상수 하나가 여러 항목을 동시에 망친다.**

| 상수 | 초기 추측 | 조문 확정 | 근거 |
|---|---|---|---|
| 고시금액 (물품·용역) | 2억 2천만 | **2억 3천만** | 재정경제부 고시 2026-439 제1호 가목 |
| 공동수급 지분율 (국가) | 5% | **10%** | 공동계약운용요령 제9조 ⑤ 나목 |
| 공동수급 지분율 (지방) | 10% | **5%** | 지방 집행기준 제6장 |
| v3 비교 기준 | 배정예산 | **추정가격의 1배** | 국가계약법 시행규칙 제25조 ② 1호 나목 |
| v23 공고기간 | 5일 고정 | **10/20/40일** | 지방계약법 시행령 제35조 ⑤ |

### 3.1 지분율이 정확히 반대였다

국가 5% / 지방 10%로 알고 있었는데, 조문상 **국가 10% / 지방 5%** 였다. 고치자 v21의 F1이 **0.500 → 1.000**이 됐다.

### 3.2 고시금액 2.3억의 교차 검증

이 상수는 dev에서 **완전히** 확인된다. 2.3억 경계로 자르면:

```
v14  양성 8/8  →  전부 고시금액 이상       ✅
v15  양성 6/6  →  전부 1억 ~ 고시금액       ✅
v16  양성 6/6  →  전부 1억 ~ 고시금액       ✅
v17  양성 6/6  →  전부 1억 미만            ✅
v18  양성 7/7  →  전부 1억 미만            ✅

한 건도 어긋나지 않는다.
```

**분석**: 이것이 좋은 상수 검증의 형태다. 상수를 넣어 점수가 올랐다는 것이 아니라, **상수가 만드는 구간 분할이 라벨의 구조와 완전히 일치한다**는 것을 보인다. 33건의 양성이 예외 없이 분할선을 지킨다면 그 분할선은 우연이 아니다. §5에서 다룰 "채택 기준"의 모범 사례이기도 하다 — dev 점수가 아니라 **구조적 일치**가 근거다.

## 4. 핵심 설계 (3) — 시간 예산을 구조로 강제한다

### 4.1 사고: 2시간 초과 = 제출 오류

v6·v7이 2시간을 넘겨 **제출 오류**를 냈다. 점수 0이 아니라 **채점 자체가 실패**했다. 하루 1회 제출이므로 이 사고 하나가 이틀을 태웠다.

```
원인 분석

  평가셋 1,853건 기준 prefill = 45.5M 토큰
        │
        └─ 시간 가드가 vLLM 배치 루프 안에만 있었다
                │
                ├─ dense 인코딩         ← 가드 밖에서 예산 소진
                └─ 프롬프트 사전 생성    ← 가드 밖에서 예산 소진
```

**교훈**: 시간 가드를 "가장 오래 걸리는 단계"에 붙이면 안 된다. 예산은 **프로세스 전체가 공유하는 단일 자원**이어야 한다.

### 4.2 세 겹 방어

```
┌───────────────────────────────────────────────────────────────┐
│ 1. RunBudget — 단일 데드라인                                    │
│                                                               │
│    프로세스 시작 기준 6,300초 (공식 7,200초 대비 15분 여유)       │
│    모든 단계가 이 하나를 공유한다                                 │
│    → 어떤 단계도 "내 몫"을 따로 갖지 않는다                       │
└───────────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────────┐
│ 2. SubmissionWriter — 항상 유효한 제출 파일                      │
│                                                               │
│    GPU를 켜기 ★전에★ 규칙 기반 49열 CSV를 먼저 쓴다              │
│    배치마다 갱신                                                │
│    SIGTERM / atexit 핸들러 포함                                 │
│    → 강제 종료돼도 유효한 제출 파일이 남는다                       │
└───────────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────────────────────┐
│ 3. tier ladder — 무엇을 포기할지 미리 정한다                      │
│                                                               │
│    시간이 모자라면 ★항목이 아니라 검색 깊이★를 줄인다              │
│    full → lean → tight → minimal                              │
│    → 24개 항목은 끝까지 전부 살아 있다                            │
└───────────────────────────────────────────────────────────────┘
```

### 4.3 설계 분석

세 장치가 각각 다른 실패 양상을 막는다.

| 장치 | 막는 실패 | 원리 |
|---|---|---|
| RunBudget | 특정 단계가 예산을 독식 | 자원을 전역화 |
| SubmissionWriter | 완주 실패 시 산출물 0 | **결과를 앞당겨 확정**하고 점진 개선 |
| tier ladder | 시간 압박 시 항목 포기 | **열화 방향을 사전 지정** |

특히 2번이 구조적으로 우수하다. 보통은 "다 끝나면 파일을 쓴다"고 짜지만, 여기서는 **최악의 결과(규칙 전용)를 먼저 디스크에 쓰고** 모델 결과로 덮어쓴다. 그 결과 **실패 모드가 "제출 오류"에서 "점수가 조금 낮음"으로 바뀐다.**

3번도 같은 사고방식이다. 시간이 모자랄 때 무엇을 버릴지 코드가 미리 알고 있으면, 런타임에 임의로 항목을 버리는 일이 생기지 않는다. §1.2(a)에서 본 대로 **항목 하나를 버리면 F1이 구조적으로 0**이 되므로, 항목은 절대 포기 대상이 될 수 없다.

**실측 결과**: 48분 26초 완주 (한도 120분), prefill 45.5M → **13.9M**, 공고당 2호출.

## 5. 핵심 설계 (4) — 채택 기준은 dev 점수가 아니라 외부 근거다

이 프로젝트에서 가장 값비싸게 배운 원칙이다.

### 5.1 전이율 측정

| 구간 | dev | test | 전이율 |
|---|---:|---:|---:|
| v14 → v21 | +0.0548 | +0.0131 | **24%** |
| v21 → v23 | −0.0025 | +0.0043 | **음수** (dev를 내리고 test를 올림) |
| v23 → v25 | +0.0067 | +0.0050 | **75%** |

### 5.2 원인 — dev 표본 위에서 고른 변경

v14→v21 구간에는 **dev 표본을 보고 고른 변경**이 섞여 있었다. 예: *"dev에서 양성이 0인 항목만 골라"* 게이트를 적용하는 식.

그것들을 제거하자 **dev는 내려갔는데 test는 올랐다** (v21→v23).

v23→v25는 전부 외부 근거 유형이었고 전이율이 **3배**였다.

```
[ 왜 이런 일이 생기는가 ]

  dev 200건 · 항목당 양성 5~8건
        │
        └─ "dev에서 양성이 0인 항목" 같은 조건은
           그 항목의 성질이 아니라 ★200건 표본의 우연★을 기술한다
                │
                └─ test 1,853건에서는 그 우연이 재현되지 않는다
                        │
                        └─ dev만 오르고 test는 안 오르거나 내려간다
```

### 5.3 채택 규칙

```
✅ 채택 — 외부 근거 유형
   · 법령 조문
   · 항목표 비고
   · 운영진 답변
   · 데이터 형식
   · 데이터 품질
   · 논리 버그 수정

❌ 기각 — 표본 유래 유형
   · dev 표본에서 고른 임계값
   · dev 표본에서 고른 항목 조합
   · 근거 없이 dev만 오르는 변경
```

**핵심**: 이 규칙의 판정 대상은 **결과가 아니라 근거의 출처**다. "dev가 올랐는가"를 묻지 않고 **"이 변경을 정당화하는 문서가 dev 바깥에 있는가"** 를 묻는다.

§1.2(d)에서 본 대로 개별 변경은 리더보드로 검증할 수 없다. 검증할 수 없다면 **검증 대신 근거로 판단**해야 한다. 이 원칙이 4연속 갱신을 만들었다.

## 8. 기각한 것 8건 — 음성 결과 기록

시도 20건 중 채택 12건, **기각 8건**이다. 기각도 기록한다. 같은 길을 다시 걷지 않기 위해서다.

| 시도 | 결과 | 이유 |
|---|---|---|
| **dense/hybrid 검색 (vector DB)** | **상한이 음수** | 정답 근거를 강제 주입해도 0.6488 → **0.5993**. gold 근거의 **96.3%가 이미 프롬프트에 들어간다** |
| 근거 증감 (4k / 9k) | 0.6064 → 0.5950 / 0.5820 | 6,000자가 국소 최적 |

| 필드 1개 추가 (`조달_품목명`) | 0.6009 → 0.5497 | **무관한 항목까지 붕괴** (v6 −0.350) |
| 4호출 분할 | 0.6800 → 0.6712 | 그룹당 5~13필드는 문맥이 너무 얕다 |
| **자기일관성 앙상블** | **설계 불성립** | 2회는 동점, 3회는 **124분**으로 시간 초과. 규칙을 tie-breaker로 쓰면 모든 필드에서 진다 (−0.002 ~ −0.033) |
| 표적 재추출 (약한 필드만 재질의) | 0.6667 → 0.6299 | v9가 0.615 → **0.000**. 조항 발췌가 참가자격 섹션만 봐서 모델명(규격서 소재)에 빈 문맥을 준다 |

### 8.1 가장 값진 음성 결과 — dense 검색의 상한이 음수

```
실험: 정답 근거(gold evidence)를 강제로 프롬프트에 주입한다
      → 검색 성능의 ★이론적 상한★을 측정하는 셈

결과: 0.6488 → 0.5993   (상한이 현재보다 낮다)

원인: gold 근거의 96.3%가 이미 프롬프트에 들어가 있다
      추가 주입은 정보를 늘리지 않고 ★문맥만 흐린다★
```

**이 실험 설계 자체가 이 프로젝트에서 가장 유용한 도구였다.** "검색을 개선하면 얼마나 오를까"를 묻는 대신 **"완벽한 검색이라면 얼마나 오를까"** 를 먼저 측정했다. 상한이 음수로 나왔으므로 vector DB 구축에 들일 시간 전부를 아꼈다.

RAG 파이프라인을 개선하려는 모든 프로젝트가 이 측정을 먼저 해야 한다. **retrieval이 병목이 아닌데 retrieval을 고치는 일**이 매우 흔하다.

### 8.2 프롬프트 변경은 국소적이지 않다

필드 하나(`조달_품목명`)를 추가했을 뿐인데 **무관한 항목 v6이 −0.350** 붕괴했다.

이는 고정 모델 환경의 근본 난점이다.

```
파인튜닝 가능        →  변경의 영향 범위를 데이터로 제한할 수 있다
파인튜닝 금지 (여기)  →  레버가 프롬프트뿐인데, 프롬프트 변경은 전역적이다
                       → 한 항목을 고치려다 다른 항목이 무너진다
                       → 프롬프트 실험 10회 중 성공 1회 (§9)
```

2. **자가 라벨링** — 층화 표본 3,000건. 다만 v21·v22·v24 등 여섯 항목은 train에 거의 없어(각 3~9건) 접근 가능한 여력이 **Macro +0.082로 제한**된다
3. **배치 라벨링 계속** — v17 18건 완료, 나머지 미착수

법령패키지는 정독을 마쳤고, 외부 법령 추가는 규정상 금지다 (*"판정 기준은 배포된 법령 패키지의 스냅샷으로 고정"*).

## 10. 정리 — 이 대회에서 이전 가능한 것

### 원칙 1. 모델에게 판정이 아니라 추출을 시켜라

판정을 코드로 옮기면 테스트·귀속·캐시·하한이 전부 따라온다. 0.127 → 0.311, 침묵 항목 18 → 1.

### 원칙 2. 상수는 추측하지 말고 원전에서 확정하라

특히 항목들이 같은 트리거를 공유하고 상수로 갈리는 구조에서는, 상수 하나가 여러 항목을 동시에 좌우한다. 지분율 반전 하나로 v21이 0.5 → 1.0.

### 원칙 3. 실패 모드를 "산출물 없음"에서 "점수 낮음"으로 바꿔라

GPU를 켜기 전에 규칙 기반 제출 파일을 먼저 쓴다. 시간이 모자라면 항목이 아니라 검색 깊이를 줄인다. 완주 실패는 점수 0이 아니라 **제출 오류**다.

### 원칙 4. 검증할 수 없다면 근거로 판단하라

하루 1회 제출 · 2σ 검출 한계 +0.089 · 실제 최대 변경 +0.032 → 개별 변경은 검증 불가능하다. 이때 판단 기준은 결과가 아니라 **근거의 출처**여야 한다. 외부 근거 유형만 채택했을 때 전이율이 24% → 75%로 올랐다.

### 원칙 5. 개선 전에 상한을 먼저 측정하라

정답 근거를 강제 주입해 검색의 이론적 상한을 재보니 **음수**였다. gold 근거의 96.3%가 이미 프롬프트에 있었다. 이 한 번의 측정이 vector DB 구축 시간 전부를 아꼈다.

### 원칙 6. 음성 결과를 기록하라

시도 20건 중 8건이 기각이다. 기각 목록이 없으면 같은 실험을 다시 하게 된다. 특히 §8의 표는 "이미 해봤고 안 된다"를 근거와 수치로 남긴다.
