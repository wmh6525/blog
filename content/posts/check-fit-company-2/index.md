방문자가 자기 기기에서 계산한다면 운영 컴퓨터는 주로 화면 파일을 전달하면 된다. 이 편은 내 맥북으로 그 일을 맡겨 보고 서비스 운영의 조건을 살펴본다. 파일을 빨리 전달하는 것과 계속 접속할 수 있게 하는 것은 별개다.

**먼저 알아둘 말**

- [브라우저·서버]({{< relref "ai-glossary" >}}#web): 브라우저는 사용자가 웹페이지를 여는 프로그램이고, 서버는 요청을 받아 파일이나 데이터를 제공하는 쪽이다.
- [배포·운영]({{< relref "ai-glossary" >}}#deployment): 배포는 만든 프로그램을 사용자가 접근할 수 있는 환경에 올리는 일이다. 운영은 그 뒤 계속 사용할 수 있도록 관리하는 일이다.
- [지연·처리량]({{< relref "ai-glossary" >}}#latency): 지연은 요청 하나의 결과를 기다리는 시간이고, 처리량은 일정 시간에 처리하는 작업의 양이다. 둘은 같은 지표가 아니다.

## 1. "운영은 내 M1 맥북 에어에서 할 거야"

첫 버전을 만든 뒤 붙인 조건은 이것이었다.

> 중요한 건 운영을 내 M1 맥북 에어 16GB에서 서빙할 수 있어야 돼.

따로 서버를 빌리지 않고 쓰던 노트북으로 서비스해 보고 싶었다.

## 2. 노트북으로도 충분한 이유

이 앱은 계산을 **전부 사용자의 브라우저에서** 한다([1편]({{< relref "posts/check-fit-company-1" >}}) 참고). 서버가 하는 일은 HTML, CSS, JavaScript, 아이콘 같은 **파일을 내려주는 것뿐**이다.

식당에 비유하면 손님이 각자 자리에서 요리하고 서버는 재료 상자만 건네주는 셈이다. 계산을 손님 쪽에서 하니 서버가 맡는 일은 적다.

다만 개발할 때 쓰던 `python3 -m http.server`는 말 그대로 개발용이라 운영에는 맞지 않는다. 운영에 필요한 것을 정리하면 이렇다.

| 필요한 것 | 왜 필요한가 |
|---|---|
| 운영용 서버 | 압축, 캐시, 보안 헤더를 제대로 처리해야 한다 |
| 자동 시작·재시작 | 맥을 재부팅하거나 서버가 죽어도 다시 떠야 한다 |
| 잠자기 방지 | 맥이 잠들면 서비스도 멈춘다 |
| 외부 공개(HTTPS) | 집 밖의 사람도 접속할 수 있어야 한다 |

작업 중인 컴퓨터의 사양을 확인해 보니 바로 그 **MacBook Air (M1, 16GB)** 였다. 덕분에 운영 환경과 똑같은 기기에서 직접 부하 테스트를 할 수 있었다.

이 구조에서 사용자가 늘면 서버가 반복하는 일은 주로 화면 파일을 전달하는 것이다. 사주와 색 계산은 각 사용자의 기기가 맡는다. 다만 파일을 빨리 보내는 능력과 서비스를 계속 열어 두는 일은 별개다. 뒤의 부하 테스트는 전자를 살펴보고, 절전·자동 실행·외부 접속 문제는 후자를 다룬다.

## 3. 설치할 것 없는 운영용 서버

맥에 이미 Node.js가 깔려 있어서 **추가 설치 없이 Node만으로** 서버를 만들었다.

- **내보낼 파일 분리**: 웹 파일을 `public/` 폴더로 옮겨 그 폴더만 내보낸다. 테스트 코드나 서버 코드가 밖으로 새지 않는다.
- **압축**: 파일을 미리 압축해 둔다. 예를 들어 `app.js`는 14KB에서 4KB로 줄었다.
- **캐시 확인**: 브라우저가 "이 파일 바뀌었어?" 하고 물으면, 안 바뀐 경우 "그대로야(304)"라고만 답해 데이터를 아낀다.
- **보안 헤더**: 다른 사이트가 이 앱을 몰래 끼워 넣지 못하게 하고 허락한 곳의 스크립트만 실행되게 하는 설정(CSP)을 넣었다.

나쁜 요청이 막히는지도 하나하나 확인했다.

| 시도한 요청 | 결과 |
|---|---|
| `/../server.mjs` (상위 폴더의 서버 코드 훔쳐보기) | ✅ 400 차단 |
| `/%2e%2e/server.mjs` (같은 시도를 인코딩으로 숨김) | ✅ 400 차단 |
| `/.DS_Store` (맥의 숨김 파일) | ✅ 400 차단 |
| `POST /` (파일 서버에 데이터 보내기) | ✅ 405 거부 |
| 없는 파일 | ✅ 404 |

## 4. 맥에서 항상 돌아가게 하기

macOS에는 **launchd**라는, 프로그램을 자동으로 실행해 주는 관리자가 있다. 이를 이용해 스크립트 하나로 설치·재시작·상태 확인을 할 수 있게 했다.

- **자동 시작**: 맥에 로그인하면 서버가 켜진다.
- **자동 재시작**: 서버가 죽으면 launchd가 다시 띄운다.
- **잠자기 방지**: macOS의 `caffeinate` 명령으로 서버가 도는 동안 맥이 잠들지 않게 한다.
- **로그 교체**: 접속 기록이 10MB를 넘으면 새 파일로 바꾸고 3개까지만 보관한다.

### 4.1 macOS의 함정: 보호 폴더

걸리는 점이 하나 있었다. 프로젝트가 `~/Downloads`(다운로드 폴더)에 있는데, 이 폴더는 macOS의 **개인정보 보호 폴더**다. 데스크톱과 문서 폴더도 마찬가지다. 로그인할 때 백그라운드로 자동 실행되는 프로그램은 이런 폴더의 파일을 못 읽을 수 있다.

그래서 운영용 파일은 `~/Library/Application Support/` 아래에 **따로 복사해서** 거기서 실행하게 했다. 개발 폴더와 운영 폴더가 분리되는 장점도 있다.

## 5. 정말 버틸까? 부하 테스트

동시 접속 100명이 20초 동안 쉬지 않고 첫 화면을 요청하는 상황을 만들어 봤다.

| 항목 | 결과 |
|---|---|
| 20초 동안 처리한 요청 | 약 **55만 7천 건** |
| 초당 처리량 | 약 **28,000건** |
| 평균 응답 시간 | **3ms** |
| 대부분의 응답 시간 | 10ms 이내 |
| 서버 메모리 | 55만 건 처리 후에도 **75MB** |

16GB 메모리 중 75MB만 쓰면서 초당 2만 8천 건을 처리했다. 재미용 앱으로는 차고 넘치는 성능이다. 압축과 보안 헤더가 걸린 상태에서도 앱이 정상 동작하는지 브라우저로 다시 확인했고 콘솔 에러는 없었다.

## 6. 그런데 남은 숙제들

성능은 문제가 아니었다. 남은 건 **운영의 번거로움**이었다.

1. **노트북 덮개를 닫으면 잠든다.** `caffeinate`로도 못 막아서, 외부 모니터를 연결하거나 덮개를 열어 둬야 한다.
2. **맥북을 들고 나가면 서비스가 멈춘다.**
3. **외부에 공개하는 방법**: 집 인터넷을 밖에 열려면 공유기 설정이 필요하다. Cloudflare Tunnel을 쓰면 공유기 설정 없이 HTTPS로 공개할 수 있고 집 IP도 숨길 수 있어서, 이 방법을 준비하던 중이었다.

## 7. 방향 전환: "Supabase랑 Vercel로 할 수 있나?"

외부 공개를 준비하던 중에 다른 질문을 던졌다.

> supabase db랑 vercel 배포식으로 진행할 수 있나?

앞서 말한 "맥북에서 운영해야 한다"는 조건과 부딪히는 질문이라, Claude는 두 가지를 확인했다.

**어디서 서비스할까?**

| 선택지 | 장단점 |
|---|---|
| **Vercel로 운영** ← 선택 | 맥북을 켜 둘 필요가 없다. HTTPS와 전 세계 CDN이 자동. 무료(Hobby) 플랜은 비상업용만 허용 |
| 맥북에서 운영 유지 | 지금 만든 서버 + Cloudflare Tunnel. 맥북이 꺼지면 서비스도 멈춘다 |
| 둘 다 | 평소엔 Vercel, 맥북은 백업 |

**DB에 무엇을 저장할까?** 결과 공유 링크, 회사 정보, 회원과 기록, 통계와 랭킹 중에서 고르라는 질문이었고 **네 가지 모두** 하기로 했다.

이렇게 맥북은 **개발용**이 되고 운영은 Vercel로 넘어갔다. 만들어 둔 Node 서버와 자동 실행 스크립트는 더 필요 없어서 지웠다. Vercel이 같은 일(압축, 캐시, 보안 헤더)을 대신해 주기 때문이다.

## 8. 정리

- 계산을 브라우저에서 하는 앱이라면 **M1 맥북 에어로도 성능은 충분**하다. 초당 2만 8천 건, 메모리 75MB였다.
- 다만 노트북 서버는 **항상 켜져 있어야 한다**는 게 가장 큰 부담이다. 덮개, 외출, 재부팅, 외부 공개가 모두 신경 쓸 거리다.
- 작업 결과는 결국 지웠지만 이때 정리한 보안 헤더와 캐시 설정은 다음 편의 Vercel 설정으로 그대로 옮겨갔다.
