## 처음 읽는 분을 위한 안내

**학습 위치:** [앱을 만들고 운영하는 사례]({{< relref "learn" >}}#engineering).

이 글은 홈런 더비 프로젝트의 2026년 10월 27일 코드와 개발 기록을 바탕으로 정리한 제작기다. 게임의 입력이 판정·보상으로 바뀌는 과정과, 브라우저에서 계산한 결과를 서버가 어떻게 확인하는지 살펴본다.

JavaScript의 함수와 객체를 알면 코드 예제를 따라가기 쉽다. Canvas는 브라우저에서 그림을 그리는 도구이고, DB는 선수 기록과 보유품을 저장하는 곳이라고 이해하고 읽어도 된다.

>

## 1. 공이 오는 순간 한 번 누르면 된다

홈런 더비의 조작은 하나다. 투수가 던진 공이 홈플레이트에 도착하는 순간 화면을 누른다. 컴퓨터에서는 스페이스바로도 칠 수 있다.

정확하게 맞히면 공이 멀리 날아가고, 홈런으로 얻은 골드로 선수를 강화한다. 3아웃이면 한 판이 끝난다. 다음 판에는 조금 더 높은 기록을 노린다.

```text
투구 → 탭 → 타격 판정 → 타구와 보상
                ↑              ↓
             다음 투구      3아웃이면 결과
                               ↓
                         강화·장비 → 재도전
```

조작은 짧지만 반복할 이유가 필요했다. 그래서 타격에 더해 성장과 수집, 기록 경쟁을 붙였다.

| 요소 | 현재 구현한 내용 |
|---|---|
| 타격 | 직구·체인지업·커브·슬라이더·너클볼, 타이밍에 따른 판정 |
| 성장 | 파워·컨택·집중력·스폰서 강화, 각각 최대 50레벨 |
| 꾸미기 | 배트·의상·구장, 수집품과 타구 궤적·닉네임 효과 |
| 도전 | 라이벌 5명과 기록 대결, 출석과 일일 미션 |
| 기록 | 오늘·역대 랭킹, 최장 비거리·총 비거리·홈런 수 |
| 공유 | 경기 결과를 이미지로 공유하거나 PNG로 저장 |

라이벌은 정해진 상대 기록을 넘기는 방식이다. 두 사람이 동시에 접속하는 실시간 대전은 구현하지 않았다.

## 2. 화면은 브라우저, 기록 확정은 서버

프런트엔드는 프레임워크 없이 JavaScript와 Canvas로 만들고, Vite로 빌드한다. Vercel이 화면 파일을 제공하고 Supabase가 선수 데이터와 경기 검증을 맡는다.

```text
Vercel ── HTML·CSS·JavaScript·아이콘 ──→ 사용자 브라우저
                                          │
                             그림·소리·입력·타격 연출
                                          │
                             경기 시작 / 타격 입력 전송
                                          ↓
                            Supabase Edge Function
                             공통 규칙으로 경기 재계산
                                          ↓
                              DB: 골드·장비·검증 기록
```

로컬에서는 Supabase 환경 변수 없이 브라우저 저장만으로 실행할 수 있다. 온라인으로 연결된 모드에서는 서버가 기록과 보상을 확정하며 네트워크 연결이 필요하다. 로컬 기록을 그대로 검증 랭킹에 올리는 구조는 아니다.

화면과 규칙도 나눴다. `src/main.js`는 입력·게임 진행·그리기를 맡고, `supabase/functions/_shared/`는 타이밍 판정과 보상 같은 공통 규칙을 담는다. `src/rules.js`를 통해 브라우저에서도 같은 규칙을 가져온다.

이 분리 덕분에 화면 없이도 타격 결과를 계산하고, 서버에서도 같은 경기를 다시 계산할 수 있다.

## 3. 타격의 핵심은 시간 차이

판정의 기준은 **공이 도착할 예정인 시각과 사용자가 누른 시각의 차이**다. 빠르게 누르면 음수, 늦게 누르면 양수인 밀리초 단위 오차가 된다.

초반 투구에서 컨택 강화가 없을 때 판정은 다음과 같다.

| 타이밍 오차의 절댓값 | 판정 |
|---|---|
| 25ms 이하 | PERFECT |
| 55ms 이하 | GREAT |
| 95ms 이하 | GOOD |
| 150ms 이하 | WEAK |
| 그보다 큼 | MISS |

컨택을 강화하면 허용 폭이 넓어진다. 반대로 한 판에서 오래 살아남을수록 판정 폭이 좁아지고 공도 빨라진다. 첫 3구에는 기본 판정을 유지하고 4구부터 점차 어렵게 만들었다.

판정 이름만으로 홈런이 결정되지는 않는다. 오차에서 타구의 질을 계산하고, 파워·방향·작은 무작위 변동을 반영해 비거리를 구한다. 그 방향의 펜스를 넘었는지도 확인한다.

### 강화해도 타이밍은 중요하게

파워가 모든 타구를 똑같이 멀리 보내면, 강화 뒤에는 대충 쳐도 홈런이 나올 수 있다. 그래서 파워의 추가 효과를 타구의 질 `q`의 제곱에 비례하게 했다.

아래는 실제 계산에서 핵심만 가져온 부분이다. `q`는 0부터 1 사이이고 정타일수록 1에 가까워진다.

```js
const baseDistance = 285 + 200 * Math.pow(q, 1.15);
const powerBonus = baseDistance * (m.power - 1) * q * q;
```

`q = 1`이면 파워의 추가 효과를 전부 받고, `q = 0.5`이면 그 효과의 25%를 받는다. 선수가 성장해도 정확하게 눌렀을 때의 보상이 크게 남도록 만든 것이다.

## 4. 벡터로 그리고 도트로 바꾸기

도트 그림을 모두 별도 이미지로 준비하는 대신, Canvas 도형으로 장면과 캐릭터를 그린 뒤 저해상도 화면으로 표현한다.

처리 흐름은 다음과 같다.

1. 화면 높이를 기준으로 낮은 해상도의 캔버스를 만든다.
2. 배경과 캐릭터를 도형으로 그린다.
3. 색을 정해 둔 팔레트의 가까운 색으로 바꾼다.
4. 배경에는 디더링을 적용하고 캐릭터에는 1픽셀 외곽선을 넣는다.
5. 픽셀 경계를 흐리지 않고 확대해 표시한다.

디더링은 서로 다른 색의 작은 점을 섞어 중간색처럼 보이게 만드는 방식이다. 캐릭터 외곽선은 잔디나 관중석과 몸이 섞여 보이는 것을 줄인다.

이 처리는 `src/pixel.js`에 모았다. 타자와 투수는 `drawBatter`, `drawPitcher`에서 그리므로, 의상이나 배트가 바뀌었을 때 실제 플레이 모습에도 적용할 수 있다. 구장은 팔레트와 배경 요소를 바꾸되 성능 차이는 두지 않았다.

## 5. 성장과 수집을 붙이기

강화는 네 종류다. 파워는 정타 비거리, 컨택은 타이밍 허용 폭, 집중력은 홈런 보너스 골드, 스폰서는 골드 배율을 올린다.

최대 레벨을 50까지 늘리면서 후반 효과는 완만하게 증가하도록 했다. 기존 상한까지는 원래 증가량을 유지하고, 그 이후 효과 계산에는 로그 곡선을 쓴다. 높은 레벨에서도 성장할 수 있지만 같은 폭으로 끝없이 강해지지는 않는다.

장비에는 외형과 효과를 함께 넣었다. 프라이팬이나 고등어처럼 야구 방망이와 다른 물건을 들고 칠 수 있고, 장착 배트에 따라 파워·컨택·골드 효과가 달라진다. 의상과 구장은 꾸미기 요소다.

덕아웃 자판기에는 배트·의상·궤적·닉네임 효과를 합쳐 수집품 20종을 넣었다. 중복 아이템은 조각으로 바꾸고 원하는 아이템으로 교환할 수 있다. 일정 횟수 동안 높은 등급을 얻지 못하면 보장하는 규칙도 있다.

여기서 중요한 것은 연출과 지급의 구분이다. 화면에서 개봉 애니메이션을 건너뛰어도 실제 결과는 바뀌지 않는다. 서버가 추첨·골드 차감·보유품 추가를 한 거래로 처리하고, 같은 요청을 다시 보내도 이미 정한 결과를 돌려준다.

## 6. 랭킹이 생기면 브라우저의 숫자를 믿을 수 없다

브라우저에서 돌아가는 게임은 사용자가 실행 코드나 저장 데이터를 바꿀 수 있다. 화면에 표시된 골드와 비거리를 그대로 저장하면 임의의 점수도 받아들이게 된다.

현재 구조에서는 브라우저가 최종 점수를 제출하는 대신, 서버가 시작한 경기의 타격 입력을 보낸다.

1. 서버가 경기 ID, 무작위 시드, 현재 강화·장비 설정을 발급한다.
2. 브라우저가 같은 설정으로 투구를 보여주고 입력을 받는다.
3. 타격 오차 또는 미스 입력을 서버로 전송한다.
4. 서버가 같은 규칙과 난수열로 비거리·아웃·골드를 다시 계산한다.
5. 확정된 보상만 지급하고, 3아웃으로 끝난 경기를 검증 랭킹에 반영한다.

시드는 무작위 값의 출발점이다. 같은 시드와 투구 번호를 쓰면 화면과 서버에서 같은 공을 계산할 수 있다. 그래서 “이 타이밍으로 눌렀다면 어떤 결과가 나와야 하는가”를 비교할 수 있다.

이미 확정한 입력을 바꾸거나, 경기가 끝난 뒤 입력을 더 보내거나, 정상 투구에 필요한 시간보다 지나치게 빨리 제출하는 요청도 검사한다. 골드는 확정된 누적 보상에서 이미 지급한 금액을 뺀 만큼만 추가한다. 응답을 받지 못해 재전송해도 보상이 두 번 늘어나지 않게 하기 위해서다.

구매도 서버의 가격표와 잔액으로 판단한다. 일반 저장 요청으로 골드·강화·장비·기록을 임의 변경하는 것은 거절한다. 예전 기록은 보존하되 새 검증 기록과 구분했다.

**다만 서버 재계산이 실제 사람의 입력을 증명하지는 않는다.** 화면을 그리려면 클라이언트에도 투구 정보가 필요하므로 자동으로 타이밍을 맞추는 봇은 별도 문제다. 현재 구현은 점수·잔액의 직접 위조와 중복 지급을 막는 범위로 이해해야 한다.

## 7. 휴대폰에서 화면을 잠갔다 돌아왔을 때

웹 게임은 탭 전환이나 화면 잠금을 고려해야 한다. 브라우저가 애니메이션을 멈췄다가 다시 실행하면, 돌아오자마자 공이 이미 지나가 있거나 루프가 중복으로 돌 수 있다.

현재 코드는 화면이 숨겨지면 렌더링을 멈추고, 복귀 시 투구와 연출의 기준 시간을 보정한다. `visibilitychange`, `pageshow`, `resume`, `focus`처럼 여러 복귀 이벤트가 이어져도 루프를 한 번만 다시 예약한다.

입력과 프레임 계산에는 같은 `performance.now()` 시계를 사용한다. 복귀 직후 프레임과 입력이 서로 다른 시각을 기준으로 처리되는 상황을 줄이기 위해서다.

수동 일시정지도 따로 관리한다. 사용자가 직접 멈춘 경기는 화면 잠금을 풀었다고 자동으로 재개되면 안 된다. 랭킹 화면을 열었다 닫는 경우에도 이전 정지 상태를 유지한다.

타구 비행을 건너뛰는 기능 역시 결과 계산과 분리했다. 스킵 버튼을 여러 번 눌러도 비거리나 골드는 정상 재생 때와 같아야 한다.

## 8. 밸런스와 동작을 어떻게 확인했나

규칙을 화면과 분리해 두었으므로 자동으로 여러 경기를 계산할 수 있다. `scripts/balance.mjs`는 타이밍 오차 분포를 가정하고 판당 홈런 수·골드·강화에 필요한 판 수를 비교한다.

```bash
npm run balance -- 1000
```

이 값은 **가정한 입력으로 계산한 시뮬레이션**이다. 실제 사용자의 손가락 반응이나 휴대폰 입력 지연을 측정한 수치는 아니다. 파워 강화가 빗맞은 타구까지 너무 쉽게 홈런으로 만드는지처럼 규칙을 비교하는 데 쓴다. 실제 난이도와 성장 속도는 플레이 데이터를 보고 조정해야 한다.

프로젝트에는 다음 범위를 확인하는 테스트도 있다.

| 범위 | 확인하는 내용 |
|---|---|
| 타격 규칙 | 판정 경계, 난이도 변화, 강화와 보상 계산 |
| 공통 경기 계산 | 같은 시드·설정·입력에서 화면과 서버 규칙의 결과 일치 |
| 게임 진행 | 비행 스킵, 화면 복귀, 수동 정지, 보상 중복 방지 |
| 저장과 계정 | 저장 재시도, 선수 전환과 세션 분리 |
| 수집 | 등급 보장, 중복 조각, 교환과 장착 |
| DB | 소유권·직접 접근 차단·임의 저장 거절·중복 요청 처리 |

JavaScript 검사는 `npm test`, 빌드는 `npm run build`로 실행한다. DB 검사는 `npm run test:db`로 별도 실행하고 테스트 변경을 전체 롤백하도록 구성했다. 자동 검사가 실제 휴대폰에서의 시각·터치·네트워크 검사를 대신하지는 않는다.

## 9. 배포와 남은 작업

GitHub의 main 브랜치에 코드를 올리면 Vercel이 화면을 자동 배포한다. DB 마이그레이션과 경기 검증용 Edge Function은 별도로 적용한다. 화면과 서버가 같은 규칙을 사용하므로 두 쪽의 버전을 맞추는 것도 배포 작업에 포함된다.

Supabase 주소와 공개 anon 키는 브라우저 연결에 사용하지만, 서버의 결과 확정 권한을 가진 서비스 역할 키는 Edge 런타임 안에서만 사용한다. 공개 키를 숨기는 것보다 DB와 함수가 요청자의 권한을 제대로 확인하는 것이 중요하다.

홈 화면 추가를 위한 manifest와 아이콘도 넣었다. 링크 공유용 소개 이미지와 경기 결과 이미지도 만들었다. 현재는 오프라인 캐시를 제공하지 않으며, 온라인 경기 확정에는 연결이 필요하다.

아직 남은 일은 실제 휴대폰에서 화면 잠금 복귀·네트워크 지연·개봉 연출을 확인하고, 실제 플레이 데이터를 바탕으로 강화 가격과 수집 보상을 조정하는 것이다. 자동 입력 탐지와 운영 모니터링도 추가 과제로 남아 있다.

탭 한 번의 게임도 타격 규칙, 그림, 성장, 저장, 서버 검증이 연결되면 다뤄야 할 부분이 꽤 많아진다. 이번 프로젝트에서 배운 방식은 다음에 만들 숫자 야구나 순서 맞추기에도 적용할 수 있다. 먼저 작은 규칙을 완성하고, 그 규칙을 화면과 분리해 확인한 뒤 기록과 공유 기능을 붙이는 순서다.
